# C3 · 额度、价格与结算 v0.1

> 状态：`PROPOSED / 待 C1、C4 会签及 C0 批准`  
> Owner：C3 · 价格、额度与结算负责人  
> 日期：2026-07-30  
> 适用阶段：Program Gate T1 领域冻结提案  
> 兼容合同：`INTEGRATION_CONTRACT.md` v0.1（本提案不修改公共合同）

## 1. 结论摘要

1. 客户购买和使用的是“AI 视频额度”，它是整数型生产权益单位，不是人民币余额、供应商 token、可提现资产或固定时长。
2. 每项能力通过版本化 `RateCard` 明示“预计消耗、最大冻结、成功计费条件”；供应商和模型变化不改变客户已经确认的报价快照。
3. `Wallet` 是组织持有额度的账户容器。余额由 append-only `CreditLedger` 汇总得到，任何缓存余额都不是事实源。
4. 可计费任务严格遵守 `requested -> reserved -> consumed | released`。成功只从冻结额扣减，失败不形成可交付资产时全量释放。
5. 金额与额度分离记录。上游成本、平台结算价、渠道批发价、客户零售价、活动价各自有用途，不允许用一个“单价”覆盖全部语义。
6. 首版渠道收益采用逐级买断、逐级销售形成的批发差价；不按招募人数收益，不默认从终端订单向所有上级自动抽佣。
7. 本文所有人民币数字仅为 `PROPOSED 演示算例`，不构成真实售价、税务口径或客户承诺。

## 2. 范围与非目标

### 2.1 本提案负责

- AI 视频额度定义和客户展示口径。
- Wallet、额度批次和 append-only CreditLedger。
- 充值、赠送、转拨、冻结、扣减、释放、退款、过期、人工调整。
- 五层价格、价格快照、订单差价、结算与对账口径。
- 成功、失败和跨级销售算例。

### 2.2 本提案不负责

- StoryCanvas 画布、生成模型适配和任务编排实现。
- 真实支付、开票、打款、税务和会计准则落账。
- 真实客户售价、渠道底价、授信、佣金比例和提现承诺。
- Product、Capability、SKU 的最终目录，以及渠道组织关系和权限的最终定义。
- 修改控制平面数据/API 或 `INTEGRATION_CONTRACT.md`；这些由 C4/C0 在会签后落地。

## 3. AI 视频额度

### 3.1 客户定义

**AI 视频额度是平台用于购买 AI 视频生产动作的整数型权益单位。**

客户不需要理解供应商 token、GPU 秒或模型计费单位。界面必须把额度翻译为具体动作，例如：

> 标准 5 秒 720p 视频生成：预计 100 额度，最多预冻结 120 额度；仅成功形成可交付资产后按实际规则扣减。

“1 额度”本身不承诺固定人民币价值、固定视频秒数或固定模型调用量。客户可理解性来自可见的能力价目表和任务前报价，而不是把额度伪装成货币。

### 3.2 冻结规则

- 额度代码：`AI_VIDEO_CREDIT`；客户界面统一显示“AI 视频额度”。
- 仅使用正整数计量，v0.1 不允许小数额度。
- 一个 SKU 可发放一定数量额度和一组 Entitlement；额度不能替代能力授权。
- 每次任务必须绑定 `rateCardVersion` 和 `quoteSnapshotId`。
- 报价快照至少显示能力、规格、预计额度、最大冻结额、成功计费条件、有效期。
- 已确认报价不因供应商切换或上游涨价而回写。
- 额度不可提现、不可兑换法币、不计利息，除非未来经法务和财务批准另行定义。
- 客户界面和对外材料禁止出现供应商 token 或供应商秘密。

### 3.3 RateCard 提案

`RateCard` 是“能力动作如何消耗额度”的版本化规则，不是人民币价格表。

建议字段：

| 字段 | 含义 |
|---|---|
| `rateCardId/version` | 规则及不可变版本 |
| `capabilityId` | 可计量能力 |
| `meteringRule` | 按次、按成功秒数、按输出规格或组合规则 |
| `inputBand/outputBand` | 时长、分辨率、质量档位等可见规格 |
| `estimatedCredits` | 客户确认时的预计消耗 |
| `maxReservedCredits` | 任务可冻结上限 |
| `minimumChargeCredits` | 成功后的最小扣减；v0.1 可为 0 |
| `billableOutcome` | 可交付资产满足什么条件才计费 |
| `effectiveFrom/effectiveTo` | 生效窗口 |

Demo 可使用“标准 5 秒 720p = 预计 100、最多冻结 120”的锚点，但该数字在 C2 完成 Capability/SKU 目录并经 C0 批准前不得标为正式价格。

## 4. 五层价格

额度数量与金额必须分字段保存。所有金额使用货币最小单位，例如人民币分；必须记录币种、含税口径和价格版本。

| 层次 | 权威含义 | 对谁可见 | 何时固化 |
|---|---|---|---|
| 上游成本 `UpstreamCost` | 供应商对平台的估算/实际成本事实，保留供应商原始计量单位 | 平台财务/运营 | 任务估算与供应商回执时 |
| 平台结算价 `PlatformSettlementPrice` | 平台卖给直接渠道或直客的基准成交价格，也是渠道链首段成本基础 | 对应交易双方；上游成本不可见 | 订单确认时 |
| 渠道批发价 `ChannelWholesalePrice` | 某一上级组织卖给直接下级的成交价格 | 该销售边双方 | 每一销售边订单确认时 |
| 客户零售价 `CustomerRetailPrice` | 面向企业客户的公开/合同列表价 | 对应渠道与客户 | 终端订单报价时 |
| 活动价 `CampaignPrice` | 满足活动条件后替代本次成交价的限时价格 | 符合条件的买方 | 活动资格校验并下单时 |

### 4.1 价格快照

每一订单行必须固化 `PriceSnapshot`：

- `priceBookId/version`、价格层次、卖方、买方和 SKU。
- 额度数量、原价金额、折扣金额、成交净额、币种和含税标记。
- 活动/合同依据、有效期和审批依据。
- 本次额度批次的单位取得成本，仅用于差价和管理对账。

有效成交价选择顺序：

1. 符合资格且在有效期内的活动价。
2. 已批准的客户合同价。
3. 当前买卖关系适用的零售价或批发价。

上游成本不直接参与客户报价，也不能因供应商成本变化追溯修改历史订单。

### 4.2 重要分离

- `creditAmount = 100` 表示 100 个额度，不表示 100 元。
- `netAmountMinor = 1500, currency = CNY` 表示 15.00 元，不表示 1500 额度。
- 单位价格仅可由同一价格快照中的金额除以额度数量得到，用于展示和分析。
- 钱包只记额度；真实收付款和应收应付必须进入未来的资金/财务子账，不能塞进 CreditLedger。

## 5. Wallet、额度批次与 append-only CreditLedger

### 5.1 Wallet

v0.1 建议每个组织、每种额度类型只有一个主钱包：

```text
Wallet
- walletId
- organizationId
- creditType = AI_VIDEO_CREDIT
- status = active | frozen | closed
- createdAt
```

Wallet 不属于个人、品牌、门店或项目。成员能否查看或操作钱包由 Membership、Role 和数据权限决定。项目预算可在后续作为额度分配视图，不另造事实钱包。

客户可见余额：

```text
可用额度 available = Σ(wallet.available bucket 的已入账 delta)
冻结额度 reserved   = Σ(wallet.reserved bucket 的已入账 delta)
受控总额 controlled = available + reserved
```

约束：

- `available >= 0`，`reserved >= 0`。
- Wallet 表若保存余额，仅可作为可重建投影；CreditLedger 才是事实源。
- `frozen` 钱包禁止新增充值以外的业务动作，已冻结任务可按风控指令结算或释放。
- `closed` 前必须满足可用和冻结余额均为 0，或完成经批准的迁移。

### 5.2 CreditLot

每次充值、赠送、退款补偿或转入形成可追踪额度批次：

```text
CreditLot
- lotId
- walletId
- sourceType/sourceId
- originalCredits
- remainingAvailable
- remainingReserved
- issuedAt/expiresAt
- transferPolicy
- refundPolicy
- acquisitionPriceSnapshotId?
- parentLotId?
```

批次用于处理有效期、退款资格和成本基础。默认消耗顺序为“最早过期优先，过期时间相同则最早入账优先”。赠送额度默认先于无期限购买额度消耗，但具体优先级必须在套餐条款中明示。

### 5.3 CreditLedger

CreditLedger 采用“一个业务事件、一个 posting group、多条不可变分录”。建议核心字段：

| 字段 | 含义 |
|---|---|
| `entryId` | 全局唯一分录 ID |
| `postingGroupId` | 同一原子业务事件的分录组 |
| `walletId/accountId` | 客户钱包或平台系统账户 |
| `bucket` | `available`、`reserved` 或系统对手账户 |
| `delta` | 整数；正数增加该账户，负数减少 |
| `operation` | 本文定义的业务动作 |
| `lotId` | 额度批次 |
| `referenceType/referenceId` | 订单、任务、退款、活动或工单 |
| `reservationId` | 冻结链路 ID，可空 |
| `idempotencyKey` | 调用方幂等键 |
| `occurredAt/effectiveAt` | 发生时间和业务生效时间 |
| `actorType/actorId` | 系统、成员或管理员 |
| `reasonCode/note` | 结构化原因与说明 |
| `metadataSnapshot` | 价格、规则和审批快照引用 |

强制不变量：

1. 分录只能追加，禁止 update/delete。
2. 同一 `postingGroupId` 的全部 `delta` 总和必须为 0。
3. 同一业务范围内 `idempotencyKey` 唯一；重复请求返回原结果，不重复入账。
4. posting group 必须在单一数据库事务内全成或全败。
5. 错账通过“反向补偿分录 + 正确的新分录”处理，不覆盖原流水。
6. 任何扣减都能追溯到 reservation、任务回执、RateCard 和额度批次。
7. 金额字段不进入额度 delta；金额只通过订单/价格/结算快照引用。

系统对手账户至少包括：

- `PURCHASE_ISSUANCE`：付费额度发行。
- `PROMOTION_ISSUANCE`：赠送额度发行。
- `CONSUMED_SINK`：已消费额度。
- `EXPIRED_SINK`：已过期额度。
- `REFUND_RECLAIM`：订单退款回收额度。
- `ADJUSTMENT_CLEARING`：人工调整对手账户。

## 6. 九类额度动作

### 6.1 充值 `PURCHASE_CREDIT`

前置：订单已确认收款，或 Demo 明确处于模拟收款状态。

分录：

```text
PURCHASE_ISSUANCE      -N
buyer.wallet.available +N
```

- 创建 purchased lot，绑定订单行和价格快照。
- 支付回调必须幂等。
- v0.1 不允许先充值后形成无凭据的负应收；真实授信另行批准。

### 6.2 赠送 `GRANT_CREDIT`

分录：

```text
PROMOTION_ISSUANCE     -N
receiver.wallet.available +N
```

- 必须记录活动、审批人、有效期、是否可转拨。
- 默认不可提现、不可现金退款、不可转拨。
- 赠送额度产生的使用仍记录上游成本，但不伪造销售收入。

### 6.3 转拨/销售交付 `TRANSFER_CREDIT`

分录：

```text
seller.wallet.available -N
buyer.wallet.available  +N
```

- 必须是 C1 批准的直接组织关系，且卖方有销售/分配权限。
- 付费转拨绑定一张直接买卖双方的订单；免费内部划拨也必须有原因。
- 不新增平台总发行量；买方批次通过 `parentLotId` 保留来源。
- 卖方不可转拨冻结、过期、不可转让或退款锁定额度。
- 同一次跨级销售必须拆成多条直接销售边，禁止越过中间组织伪造一笔分润。

### 6.4 冻结 `RESERVE_CREDIT`

分录：

```text
wallet.available -N
wallet.reserved  +N
```

- 仅在控制平面授权通过、余额充足、报价快照有效时执行。
- reservation 绑定 `generationTaskId`、最大冻结额和到期时间。
- 不允许余额变负；并发冻结使用原子条件更新/事务。
- reservation 到期但任务无有效接单证据时自动释放。

### 6.5 扣减 `CONSUME_CREDIT`

分录：

```text
wallet.reserved -N
CONSUMED_SINK   +N
```

- 只接受幂等的成功任务回执，并达到 `billableOutcome`。
- `actualCredits <= reservedCredits`；成功额小于冻结额时，余量必须另做 `RELEASE_CREDIT`。
- 实际额大于冻结额时，先创建“补充冻结”分录；余额不足则进入人工处理，不得覆盖原冻结或制造负余额。
- 同一交付资产不得重复扣减。

### 6.6 释放 `RELEASE_CREDIT`

分录：

```text
wallet.reserved  -N
wallet.available +N
```

触发：

- 供应商失败、平台失败、用户在允许阶段取消。
- 成功后实际扣减小于最大冻结额。
- reservation 超时且生产平面没有有效接单/续期证据。

没有可交付资产的失败，v0.1 默认对客户全量释放；已产生的上游成本由平台成本记录承担或向供应商申诉，不转成客户额度扣减。

### 6.7 退款 `REFUND`

退款必须区分两种语义：

**订单退款回收**

```text
wallet.available -N
REFUND_RECLAIM   +N
```

- 仅回收原订单中仍未使用、未冻结、未转出的可退款 purchased lot。
- 可回收额度不足时，只允许部分退款或拒绝并进入人工审核；禁止让钱包为负。
- 赠送额度无现金退款价值。下游订单退款只影响直接买卖双方，不自动冲销整条上级链。

**服务额度补偿**

```text
ADJUSTMENT_CLEARING    -N
wallet.available       +N
```

- 用于成功后发现误扣、资产不可用或服务争议。
- 必须引用原 `CONSUME_CREDIT`，作为新补偿分录，不反写原消费记录。
- 是否同时退现金由订单退款流程单独决定。

### 6.8 过期 `EXPIRE_CREDIT`

分录：

```text
wallet.available -N
EXPIRED_SINK     +N
```

- 仅过期批次中尚可用的额度。
- 新 reservation 的有效期不得越过额度批次到期时间。
- 若历史异常导致到期时仍有 reserved，先让任务消费或释放；释放时若批次已经到期，同一原子流程立即转入 `EXPIRED_SINK`。
- 过期不等于现金退款，也不得静默删除批次。

### 6.9 人工调整 `MANUAL_ADJUSTMENT`

正向：

```text
ADJUSTMENT_CLEARING -N
wallet.available    +N
```

负向为相反分录。

- 必须有工单、reason code、操作者和审批人；操作者与审批人默认分离。
- 负向调整只能使用 available，不可直接减少 reserved，不得造成负余额。
- 已关闭账期的错误在下一账期用补偿分录修正。
- 人工调整不是绕过退款、赠送或转拨规则的快捷入口。

## 7. 状态机与一致性

### 7.1 生成额度状态机

```text
requested -> reserved -> consumed
                     \-> released
```

与公共合同保持一致。`consume` 和 `release` 均为终态业务结果；部分消费用“消费一部分 + 释放余量”表达。

### 7.2 订单状态提案

```text
draft -> pending_payment -> paid -> fulfilled
  \-> cancelled
fulfilled -> refund_pending -> partially_refunded | refunded | refund_rejected
```

只有 `paid` 才能发行付费额度；只有额度交付成功后进入 `fulfilled`。真实支付状态由未来支付适配层确认。

### 7.3 结算批次状态提案

```text
open -> calculated -> reviewed -> confirmed -> closed
```

关闭后禁止修改；遗漏或错账在新批次以调整项体现。

### 7.4 回执和并发

- 控制平面是客户额度状态的唯一写入方；StoryCanvas 只回传用量事实。
- 同一任务乱序收到 `success` 和 `failure` 时，以第一条合法终态回执入账，后续冲突进入异常队列。
- 供应商回执成本可以晚到，但不得因此延迟客户额度的确定性状态。
- 钱包状态、批次选择、冻结和 ledger posting 必须在同一事务边界内完成。

## 8. 批发差价优先的渠道收益

### 8.1 v0.1 规则

1. 每一渠道组织以自己的成交价从直接上级购买额度，形成自己的取得成本。
2. 它再以自己的批发价或零售价卖给直接下级/企业客户。
3. 渠道订单毛差：

```text
渠道订单毛差
= 本销售边净成交金额
- 本次售出额度的取得成本
- 本销售边承担的退款、折扣和经批准返利
```

4. 成本基础按 CreditLot 传播；部分售出按同一批次单位取得成本分摊。
5. 该指标是管理对账口径，不替代法定会计利润、税务利润或可提现余额。
6. 上级只从自己实际完成的销售边获得差价，不因下级招募或下下级成交自动获得收益。

### 8.2 结算与对账

每个结算周期按直接买卖关系生成 statement，至少包含：

- 期初/期末可用和冻结额度。
- 充值、买入、卖出、赠送、退款、过期和人工调整。
- 销售净额、取得成本、订单毛差。
- 待确认/已确认上游成本。
- 未匹配订单、任务、回执和异常调整。

Settlement 是订单、CreditLedger、任务回执和成本记录的汇总视图，不是新的余额事实源。对账单关闭后只能在后续账期追加调整。

### 8.3 后续佣金扩展点

如未来引入佣金，必须独立建 `CommissionRule/CommissionEntry`：

- 仅由已支付且超过退款窗口的真实销售/使用事件触发。
- 不写入 CreditLedger，不改变额度守恒。
- 不按招募人数、层级人数或单纯挂靠关系计提。
- 比例、封顶、税费、冲回和可提现条件必须经用户、法务和财务批准。

## 9. 三个完整算例

以下价格仅用于验证模型。

### 9.1 成功：冻结 120，扣减 100，释放 20

演示价格层：

| 项目 | 演示值 |
|---|---:|
| 上游实际成本 | ¥6.80/本任务 |
| 平台结算参考 | ¥0.10/额度 |
| 渠道批发参考 | ¥0.12/额度 |
| 客户零售价 | ¥0.18/额度 |
| 客户活动价 | ¥0.15/额度 |

企业直购 1,000 额度，活动成交金额 ¥150.00：

```text
充值后：available = 1,000, reserved = 0
任务报价：预计 100，最多冻结 120
冻结后：available = 880, reserved = 120
成功实扣 100：available = 880, reserved = 20
释放余量 20：available = 900, reserved = 0
```

关键分录：

| 动作 | available | reserved | 系统对手账户 |
|---|---:|---:|---:|
| 充值 1,000 | +1,000 | 0 | PURCHASE_ISSUANCE -1,000 |
| 冻结 120 | -120 | +120 | 0 |
| 扣减 100 | 0 | -100 | CONSUMED_SINK +100 |
| 释放 20 | +20 | -20 | 0 |

按活动价分配的本次 100 额度销售金额为 ¥15.00；上游实际成本为 ¥6.80。直销管理贡献为 ¥8.20，未计税费、退款和运营成本。平台结算参考价只用于内部比较，不再次向客户收费。

### 9.2 失败：冻结 80，客户扣减 0

企业钱包开始时 `available = 500, reserved = 0`。任务冻结 80 后供应商失败，未形成可交付资产：

```text
冻结后：available = 420, reserved = 80
失败释放：available = 500, reserved = 0
客户实际消耗：0
```

即使供应商已经向平台收取 ¥2.40，金额也只记为上游失败成本/争议成本；CreditLedger 不扣客户额度。重试必须创建新的 task、reservation 和幂等键，不复用已释放的冻结记录。

### 9.3 跨级销售：逐边批发差价

演示价格：

| 销售边 | 数量 | 单价 | 成交额 |
|---|---:|---:|---:|
| 平台 → 总代理 | 1,000 | ¥0.08 | ¥80.00 |
| 总代理 → 一级代理 | 800 | ¥0.10 | ¥80.00 |
| 一级代理 → 二级代理 | 500 | ¥0.12 | ¥60.00 |
| 二级代理 → 企业客户（活动价） | 400 | ¥0.15 | ¥60.00 |

额度结果：

```text
总代理：买入 1,000，卖出 800，剩余 200
一级代理：买入 800，卖出 500，剩余 300
二级代理：买入 500，卖出 400，剩余 100
企业客户：收到 400
```

差价：

```text
总代理毛差 = 800 × (0.10 - 0.08) = ¥16.00
一级代理毛差 = 500 × (0.12 - 0.10) = ¥10.00
二级代理毛差 = 400 × (0.15 - 0.12) = ¥12.00
渠道已实现毛差合计 = ¥38.00
```

企业客户零售价若为 ¥0.18，二级代理使用活动价 ¥0.15，相当于该销售边自行承担 ¥12.00 折扣；除非另有经批准补贴单，不能自动把折扣转嫁给上级。平台上游成本在企业实际使用额度并收到任务成本回执后确认，不把供应商 token 预先等同为这 1,000 个额度。

## 10. 异常和风控规则

| 异常 | v0.1 处理 |
|---|---|
| 可用额度不足 | 冻结失败，返回缺口；不部分冻结、不透支 |
| 重复支付/任务回调 | 命中幂等键，返回原 posting group |
| 成功回执超过冻结额 | 先尝试补充冻结；失败则进入人工异常，不制造负余额 |
| 成功与失败回执冲突 | 第一条合法终态生效，后续进入异常队列 |
| 价格版本过期 | 重新报价并由客户确认，不静默换价 |
| 额度批次即将过期 | 不创建越过到期时间的 reservation |
| 退款额度已使用/转出 | 仅退可回收部分，或拒绝并人工审核 |
| 钱包冻结 | 禁止新冻结和转出；已有任务按风控决定消费或释放 |
| 上游成本晚到 | 追加/更新成本事实，不改客户已结算额度 |
| 人工错账 | 新增补偿分录，不修改原分录 |
| 币种不同 | 不直接计算差价；须有批准的汇率快照和财务规则 |

审计最低要求：

- 管理员查看上游成本需要独立权限。
- 渠道不可查看平台上游成本和其他渠道的价格。
- 客户可查看自身订单、额度来源、冻结、扣减、释放和退款原因。
- 导出的 statement 必须能从每行下钻到订单/任务/分录。

## 11. 验收口径

- [ ] 客户页面只显示“AI 视频额度”和可理解的能力报价，不显示供应商 token。
- [ ] 任意钱包余额能完全由 CreditLedger 重建。
- [ ] 所有 posting group 借贷（delta）合计为 0。
- [ ] 生成失败没有可交付资产时，冻结额度全量释放。
- [ ] 成功扣减只来自 reserved，余量显式释放。
- [ ] 同一回调重放不会产生重复额度。
- [ ] 每笔额度可追溯到批次、订单/活动/调整和操作者。
- [ ] 每笔渠道差价只来自直接销售边，并可追溯到买入成本。
- [ ] 退款、过期、人工调整均用追加分录表达。
- [ ] 价格快照包含币种、含税口径、版本和有效期。
