# EMPLOYEE RULES · 数字员工运行规则

## 强制运行配置

1. 所有新开的 C0—C8 数字员工窗口统一使用模型 `gpt-5.6-sol`。
2. 推理强度统一设置为 `high`。
3. 运行速度统一设置为 `1.5x`。
4. C0 的每份窗口启动提示词必须明确写出模型、推理强度和运行速度。
5. 员工首次报告必须确认当前运行配置；配置不符时先暂停任务并通知 C0。
6. 未经 C0 或用户明确批准，任何员工不得自行降级、升级或切换运行配置。

## 自主调度

1. 用户正式发出启动指令后，C0 按 `AUTONOMY_PROTOCOL.md` 自主创建、调度、等待和验收 C1—C8。
2. 员工只接受 C0 或用户的正式任务，不根据其他窗口的聊天内容自行扩张范围。
3. C0 在已批准范围内处理普通技术和协作问题，不要求用户逐项确认。
4. 涉及资金、法律、授权、对外发布、不可逆操作或核心商业模式变化时必须暂停并升级给用户。

## 开工规则

1. 先读共同记忆、角色边界、自己的招聘说明和首轮任务书。
2. 开工前报告仓库、分支、已有成果、计划修改范围和明确不修改范围。
3. 只读调查完成后再写方案；没有合同不得跨仓实现。
4. 不把聊天记录当唯一事实源。

## 工作边界

1. 只修改自己拥有的文件和目录。
2. 不修改 `UI/**` 原始参考图。
3. 不重写、回滚或删除现有成果。
4. 发现意外改动立即停手并报告 C0。
5. 不直接修改其他员工的线程记忆。
6. 不向客户界面暴露上游 API Key 或供应商秘密。

## Request 协议

- 编号：`REQ-C{发起人}-{三位序号}`。
- 必填：请求内容、原因、影响范围、阻塞性、临时方案、期望 Owner。
- C0 回填：批准、拒绝、调整、负责人、目标 Gate、日期。
- 未批准的跨域 Request 不得先斩后奏。

## Handoff 协议

必须包含：基线、分支、提交、已完成、未完成、合同版本、影响范围、风险、验证证据、下游第一步。

## 提交与合并

- 一员工一任务分支/Worktree。
- 不直接推送稳定 `main`。
- 员工提交后由 C7 检查证据、C0 验收和确定合并顺序。
- 同一文件有多员工需求时，由 C0 指定唯一写入人。

## 文档纪律

- C0 单写 `COMMON_MEMORY.md`。
- C8 只能整理 C0 已批准事实。
- 方案和事实分开书写；未决内容必须标记 `PROPOSED`。
- 文档与代码冲突时，先报告，不擅自改写历史。

## 演示纪律

- Demo 数据可以 Mock，但流程、状态和商业解释必须真实一致。
- 所有关键按钮必须可操作或明确标记演示模式。
- 失败、余额不足、禁用能力和权限不足必须可解释。
- 不用“结构接近”代替视觉和业务验收。
