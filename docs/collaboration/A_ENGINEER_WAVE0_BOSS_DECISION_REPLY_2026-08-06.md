## 2. P0：组织、角色和权限决策

### P0-1 · 一个自然人属于多个组织

选择 **C：Schema 支持多组织，首版产品只开放单一活动组织上下文**。

- User、Membership 和 Session Context 按未来多组织设计。
- 首版登录只进入一个活动 Membership；不交付完整组织切换 UI。
- 切换活动组织时必须轮换 Session，不能信任客户端提交的 organizationId/tenantId。

### P0-2 · 一个 Membership 拥有多个角色

选择 **C：Schema 支持多角色，首版限制一个主角色**。

- 服务端拒绝未知角色。
- 当前 `tenant_admin`、`content_operator` 等角色继续分开。
- 老板和工作人员合并的是创作工作台体验，不是权限集合。

### P0-3 · `pilot_support`

选择 **C：兼容保留为平台支持角色，默认没有跨 Tenant 内容权限**。

- 旧白名单数据可以兼容回填。
- 跨 Tenant 协助必须使用显式、限时、带原因、可撤销、可审计的 Support Grant。
- 禁止永久全局读取客户内容。

### P0-4 · `content_operator` 创建项目

选择 **A：首版不能创建项目**。

- 项目由 `tenant_admin` 创建并分配。
- 工作人员只操作被授权项目。
- 后续如开放，必须通过新决策和权限测试，不预埋客户端绕过入口。

### P0-5 · 历史工作人员项目权限回填

选择 **C：只对白名单 Pilot 用户和项目做显式回填**。

- 海底捞等确认项目使用明确回填清单。
- 其他环境不自动授予历史全部项目 editor 权限。
- 回填结果必须可审计、可验证，不写成永久默认规则。

### P0-6 · Platform Organization 唯一性

选择 **C：首版运行时只允许一个 Platform，Schema 保留未来多 Platform 能力**。

- bootstrap 和业务服务 fail closed 保证当前只有一个活动 Platform。
- 暂不建立不可迁移的数据库全局唯一约束。

### P0-7 · 总代理、一级代理、二级代理表达

选择 **B：统一角色 `channel_admin`，层级属于 Channel Relationship，价格和提成属于版本化商业规则**。

- 不把代理等级做成登录角色。
- 不写死固定三级 Schema；首版业务限制最多总代理、一级、二级。
- 层级、可发展下级范围、归因和商业规则分别建模。

## 3. P1：注册、邀请和用户须知决策

### P1-1 · 直接注册后的组织归属

选择原问题 **A：自动创建单人 Tenant**，并冻结以下解释：

- “单人 Tenant”只是普通 Tenant 当前只有一个成员，不是独立 `consumer` 类型。
- 企业与个人共用 User、Tenant、Membership、注册 API 和统一创作工作台。
- 注册事务创建 User、Tenant、本人 `tenant_admin` Membership、Consent 和 Attribution。
- 补充企业资料或增加成员后原地成长为多人企业 Tenant，不迁移账号、项目、资产、钱包或账本。
- 不新增 C 端角色、C 端工作台、C 端 Router 或 C 端注册 API。

### P1-2 · Invitation 规则

选择 **C：定向邀请和代理分享链接同时支持**。

首版默认值：

- 定向成员邀请：绑定邮箱、7 天有效、单次使用。
- 代理分享链接：30 天有效、默认最多 100 次；平台可降低次数或提前撤销。
- 平台可以创建平台直营邀请，也可以创建指定代理归因邀请。
- 企业 `tenant_admin` 可以邀请工作人员加入指定 Tenant。
- 撤销后不能恢复；需要重新发新邀请。
- Token 只保存 digest；明文只在创建时返回一次。
- 并发使用不得突破次数；历史 Invitation Usage 不删除。

### P1-3 · 归因保护期和改绑

选择 **B：默认保护期 12 个月**。

- 从注册成功时间开始计算，规则版本和到期时间写入归因快照。
- 首次归因不可覆盖；纠错只能追加带原因、操作人和生效时间的事件。
- 改绑不追溯修改历史充值、历史额度或历史佣金。
- 保护期后的续期、转直营或重新签约使用新商业规则处理。

### P1-4 · 用户须知

选择 **B：版本发布时由业务设置 `mustReaccept`**。

- DRAFT 可编辑，PUBLISHED 不可原地修改。
- 正文变化必须发布新版本。
- 重大版本设置 `mustReaccept=true`，用户重新同意后才能继续受限操作。
- 没有 PUBLISHED 版本时公开注册 fail closed。
- 正式正文、发布人和法务审批仍待业务提供；工程师不得自拟正式条款。

### P1-5 · 注册安全首轮范围

选择 **A：受控试点安全级别**，公开运营前升级到 B。

当前必须实现：

- 邮箱验证。
- 密码强度和慢哈希。
- 找回密码。
- 注册/登录/邀请限流。
- 验证码或人机验证适配点。
- 平台管理员 MFA。
- 账号枚举保护和安全审计。

手机号验证、用户可选 MFA 和完整注册风控在公开运营 Gate 前补齐。

## 4. P2：充值、额度和代理佣金决策

### P2-1 · 批发差价和充值佣金

选择 **A：首版充值佣金替代旧批发差价**。

- 一笔订单只能进入一种代理收益模型。
- 首版不启用旧批发差价正式账。
- 历史 Demo 数据保持 `NON_QUOTE`，不迁入正式佣金账。
- 首版只有直接归因代理受益，不做多级分佣。

### P2-2 · 支付和退款

选择 **A：当前只做明确标记的 TEST Payment Adapter 和管理员人工充值**。

- 未提供支付商户主体、签名密钥和退款规则前，不接真实收款、不展示真实到账。
- Payment Provider 使用适配器边界，后续可以接微信或支付宝。
- TEST/LIVE 必须在订单、事件、页面和审计中明确区分。
- 退款、撤单和拒付使用追加冲正，不删除原事件。

真实支付渠道、币种、最低/最高金额、订单有效期和退款周期继续 fail closed，等待单独商业决策。

### P2-3 · 金额到 AI 视频额度

选择 **B：充值订单购买版本化额度 SKU，不保存可提现人民币余额**。

首版额度规则：

- 购买额度默认不过期。
- 赠送额度默认 90 天到期。
- 按最早到期批次优先消耗。
- 退款只冲正原订单尚未消费的额度；已消费不足时进入人工处理，不制造负余额绕过。
- 金钱、AI 视频额度和 Provider Token/成本继续分账。
- SKU 具体售价和包含额度未确认前仅允许测试 SKU，不对外报价。

### P2-4 · 佣金计算

选择 **A：单级直接归因佣金**。

- 受益人只有直接归因代理。
- 基数为实际支付净额，退款、撤单和拒付通过冲正扣回。
- 佣金先进入 pending，超过退款观察期后才可进入可结算状态。
- 按自然月汇总结算草稿。
- 比例、舍入和退款观察期必须来自版本化 Commission Rule，不允许散落硬编码。

佣金具体百分比尚未获得老板数值授权。A 可以完成 Rule、Accrual、Reversal 和测试 fixture，但正式规则必须保持未发布；不得自行填写 10%、20% 或 30% 并对外计提。

### P2-5 · 税务、KYC、提现和出款

选择 **A：首版只交付可审计计提和冲正账，不开放提现、不自动打款**。

- 可以生成 Settlement 草稿，但不能标记真实 paid。
- KYC、税务、开票、提现门槛、审批人和出款渠道等待后续决策。
- 页面不得承诺“可提现”或展示虚假到账。
